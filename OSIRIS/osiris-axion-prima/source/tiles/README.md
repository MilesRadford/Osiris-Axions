# Tiles algorithm with dynamic load balancing

## Overview

The "tiles" algorithm divides the simulation space into many small regions (tiles), which may be shuffled between MPI processes as a way of dynamically load balancing.  These tiles are ordered within OSIRIS as determined by one of three topologies: hilbert, snake, or rectangular.  The hilbert and snake topologies are based on space-filling curves.  The hilbert topology traces a Hilbert curve through tile space, with constraints that the smallest tile number must be a power of 2, and tile numbers in all other dimensions must be integer multiples of the smallest.  The Hilbert curve ensures that tiles close on the curve are generally close in space, which is helpful for minimizing boundary communications.  The snake topology simply traces a straight line from one edge to another, moves over by one tile, then traces back.  Node domains are usually long and skinny with snake topology, sometimes resulting in increased overhead when updating boundaries.  The rectangular topology divides the entire simulation box in the first dimension into equally balanced sections, then divides each slice separately in the second dimension (and third if necessary).  All node partitions with this topology are rectangular in shape, which can simplify boundary communications.  However, load balance will generally be better when using the space-filling curves.

All topologies are available in 2D and 3D.  When using the hilbert or snake topology, only the product of the `node_number` array in the `node_conf` section of the input deck is used (e.g., 8,1,1 is functionally equivalent to 2,2,2).  With the rectangular topology, each entry determines the number of MPI domains in that particular dimension.

The optimal tile size varies based on simulation dimension and particle number density.  Tile side length should generally be smaller in 3D than in 2D.  Tile size must be chosen carefully to attain sufficient load balance while minimizing overhead.  In our test cases using quadratic interpolation for a thermal plasma, the optimal tile side length in 2D was 16 cells when using 64 or more particles per cell (ppc), 32 cells (or slightly less) when using 16 ppc, and somewhere between 32 and 64 cells when using 1 ppc.  In 3D the optimal tile side length was 8 cells when using 8 or more ppc and 16 cells when using 1 ppc.  However, these numbers could change based on computing architecture and problem size.

Overhead of the tiles algorithm is relatively small.  Most of the overhead comes from the update boundary routines for fields and particles.  For example, when performing the dynamic load balance (DLB) every 40 time steps on a large 3D wakefield run with 512 MPI processes, the DLB only took about 1% of the total simulation time.  For the same thermal plasma tests as described above (no DLB), in 2D the tiles algorithm was actually about 1% faster than without tiles for 144 ppc; with 1 ppc the tiles algorithm was about 10% slower than without tiles.  In 3D, the overhead was usually less than 5% with many ppc, and less than 10% with only 1 ppc.  In all cases the tiles algorithm scales better with OpenMP thread number than without tiles, providing speedups between 5-60% when using 32 threads (highest speedup was in 2D with 1 ppc).  Without tiles there is extra overhead due to the current reduction, but when using tiles OpenMP parallelization is done over tiles (discussed in the following paragraph), eliminating the need for current reduction.

There are two layers of OpenMP parallelization with the tiles algorithm.  Without tiles, particles within a node are shared equally among threads and pushed in parallel.  When using tiles, parallelization of the particle push is instead done over individual tiles with a dynamic scheduler.  However, tiles are deemed "heavy" either if one or more tiles has more than 1/n_threads fraction of all particles on the node, or if there are fewer tiles than threads on a node.  After pushing all other ("light") tiles with parallelization over those tiles, heavy tiles are then pushed in serial, with particles on those tiles shared equally among threads.  This drastically improves performance when using many threads.

Since tiles are normally small regions of the simulation, it is usually advised to set `n_sort` to 0 in the `species` section of the input deck.  The default value without tiles is 25, but this could add unnecessary overhead since the particles are already relatively well sorted by being placed into tiles.  However, the `n_sort` parameter should not drastically impact speed.  It is also advisable to keep the `num_par_max` parameter in the `species` section small, since this value specifies the minimum size of the particle buffer on each *tile*.  The `grow_spec_buff` parameter in the `node_conf` section can be used to specify how many particles the buffer grows by when needed (defaults to 1024).  When performing the DLB, buffers are initialized with size `num_par_max` if their particle number is smaller than `num_par_max`, and a size of the number of particles plus `grow_spec_buff` if there are more than `num_par_max` particles in the buffer.

Finally, only some diagnostics have been functionally implemented into the tiles algorithm.  We have not been 100% clear about which diagnostics are disabled, and some are disabled silently.  Apologies for that, but it is a work in progress.  Most all emf/current diagnostics are functional.  Most phasespace, particles, and species diagnostics are functional, except for momentum distribution, temperature, heat flux, and tracking diagnostics.  Particle tracking is not supported, but ionization is.  Restarts are functional.  Vpml boundary conditions have been implemented, but are currently slow (boundary updates are not grouped by node, but all sent separately).  Lindman boundary conditions are not yet supported.

### Input parameters

* The tiles algorithm is currently implemented as a simulation mode. To activate it the following parameter must be added to the `simulation` section:
  * `algorithm = "tiles",`

* The following parameters have been added to the `node_conf` section:
  * `tile_number(x_dim)`, integer, default = 0.  Array containing number of tiles in each dimension.
  * `tile_topology`, character(*), default = "snake".  Possible values are "hilbert", "snake", or "rectangular".  The use of "rectangular" enables the topology where each node has a rectangular configuration of tiles.
  * `force_omp`, character(*), default = "default".  Possible values are "default", "heavy", or "light".  Use of "heavy" forces all tiles to be heavy tiles (threading only within tiles), and use of "light" forces all tiles to be light tiles (threading only over tiles).  It is recommended to use "default" in almost all cases.
  * `grow_spec_buff`, integer, default = 1024.  Parameter specifying how many particles to grow buffers by when full.  If this number is too large, nodes may run out of memory quickly.

* The following parameters have been added to the `grid` section:
  * `ndump_tile_node`, integer, default = 0.  Frequency at which to save node id for each tile.  Grid is of size `tile_number`, with values specifying which node id a particular tile belongs to.
  * `ndump_tile_load`, integer, default = 0.  Frequency at which to save tile load information, i.e., the number of particles per tile for all tiles.
  * `ndump_heavy_light`, integer, default = 0.  Frequency at which to save information on topology of heavy and light tiles, i.e. which tiles in the simulation space are heavy and which are light.  Grid is of size `tile_number`, with values specifying whether a tile is heavy (denoted as a 1 in the array) or light (denoted as 0 in the array). 

Note, the `load_balance` parameter in the `grid` section no longer works for each direction independently.  If any dimension of `load_balance` is set to true, load balancing is performed in all directions.
